Reachability checks

Run by the phone on its own whenever its network changes (and at start or on the app's button): which ports and protocols toward the server get through that network. "Seen as" is the phone's address as the server saw it; different addresses for different ports mean a proxy or different NAT in the path. Checks from a network the server could not be reached on are uploaded later. Newest first, all days.

Delivery timing & uplink buffering

Fast realtime UDP streams (1 ms spacing and up), one row per stream. Batched: packets reaching the receiver's kernel within 0.1 ms of each other (one uplink grant at the server, one modem-to-host transfer on the phone). 1 ms grid: how well the spacing between batches sits on 1 ms subframes (0 = no grid, 1 = exact; random ≈ 0.01–0.02). Hold: how long a batch's first packet waited for its last. Excess delay: one-way delay above the stream's fastest packet. Lines: periodicities in the arrival times that the 1 ms sender does not have, grouped by fundamental. Modem queue (overloaded streams): packets the queue holds ≈ send rate × age reached, and how often the phone's OS queue was full because the modem stopped taking packets (back pressure). Tests

One row per test. Delay down, throughput up

Moments where the delay in a bulk direction drops to half or less (by at least 20 ms) while that direction's throughput rises by at least 20 %, holding for 3 s on each side. The kind is a heuristic from the 200 ms bins and points at where to look; it does not prove the cause.

Link pauses (both directions)

Bursts of ~120 ms stalls in uplink and downlink at the same instants, with packets held rather than lost: a device-side pause (likely dual-SIM tune-away), not queueing. Exclude these windows when judging head-of-line blocking.

One-way gap episodes

Repeated gaps (> 80 ms) in one direction only, while the other direction flows normally: packets arrive in bursts after each gap (radio scheduling or queueing in that direction).

Downloads limited on the server side

Share of a test's download time running at ≥ 200 Mbit/s with < 15 ms downlink delay. There the radio is faster than the server's own link (Wi-Fi, ~280 Mbit/s), so the queue is not on the radio and downlink head-of-line blocking is not being measured.
