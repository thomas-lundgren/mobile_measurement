    Planned vs delivered rate

    Delay vs load

    Load = planned ÷ delivered rate (1 = the uplink keeps up, 2 = it carries half). p90 excess delay = how long packets waited above the stream's fastest. Expect a cliff just past 1, then a flat ceiling where the modem drops by age (per cell).

    Delivery timing & uplink buffering — all streams

    Fast realtime UDP streams (1 ms spacing and up), one row per stream. Batched: packets reaching the receiver's kernel within 0.1 ms of each other. 1 ms grid: how well the spacing between batches sits on 1 ms subframes (0 = none, 1 = exact; random ≈ 0.01–0.02). Hold: how long a batch's first packet waited for its last. Excess delay: one-way delay above the stream's fastest packet. Lines: periodicities the 1 ms sender does not have. Modem queue: packets held and the share of time the modem pushed back. Click a row for its detail.

    App traffic — simulated users beside the realtime streams

    Tests with an app_traffic flow: simulated users on the phone browse, sync mail, watch video or scroll a feed, requesting real-sized objects from the server. Wait is request → first byte (an upload: → acknowledged); done is request → last byte. An episode is what a user asked for at once, so a web_page episode's time is the page load time. Impact compares each realtime stream's extra delay (above its own minimum) and loss while any app object was in flight with the idle periods of the same test.

    Delay down, throughput up

    Moments where the delay in a bulk direction drops to half or less (by at least 20 ms) while that direction's throughput rises by at least 20 %, holding for 3 s on each side. The kind is a heuristic.

    Link pauses (both directions)

    Bursts of ~120 ms stalls in uplink and downlink at the same instants, with packets held rather than lost: a device-side pause (likely dual-SIM tune-away), not queueing.

    Congestion stalls (both directions)

    Both-direction stall bursts with shorter stalls (~95–100 ms) than a link pause (~120–130 ms): an overloaded uplink delivering in 100 ms bursts, which stalls the echoed and downlink traffic too. Kept out of the link-pause period.

    One-way gap episodes

    Repeated gaps (> 80 ms) in one direction only, while the other direction flows normally.

    Downloads limited on the server side

    Share of a test's download time at ≥ 200 Mbit/s with < 15 ms downlink delay: the radio is faster than the server's own link, so downlink head-of-line blocking is not being measured.

    Reachability checks

    Run by the phone whenever its network changes (and at start or on the app's button): which ports and protocols toward the server get through that network. "Seen as" is the phone's address as the server saw it. Newest first, all days.
